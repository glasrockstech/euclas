# Minimum first-Desktop contract profile v1

This profile specifies CP1–CP5 minimum fields, trust bindings and persistence/failure rules for fresh implementation. It does not qualify signatures, native adapters, provider entitlement, document fidelity or actual product behavior. Full-release extensions remain in the plan. Canonical field shapes are in contracts/; broader normative requirements are in requirements.md.

## Published surfaces and trust

| Packet | Exact authority | Consumer / trust restriction |
|---|---|---|
| Shared | contracts/common.schema.json | UUID/time/hash/scope/receipt/authorization/environment primitives; no identifier is a capability |
| CP1 | contracts/identity.schema.json; account.openapi.json; desktop-identity.openapi.json | Official Account store, native main and local core only for private records. Public views exclude verifier/credential refs. Account proof does not grant Membership |
| CP2 | contracts/records.schema.json Result/Evidence/Acceptance and committed_work; work.openapi.json and referenced shared-command.openapi.json components | Existing business commands and errors, same exact Work/Run edges. Trusted server derives producer/verifier/acceptor; model/request cannot self-attest them |
| CP3 | contracts/execution.schema.json | Core/engine/worker/tool adapter; never an Internet or ChatGPT-callable API. Pin source, route and current admission; gateway validates provider events before state changes |
| CP4 | contracts/documents.schema.json; generated raw_binary_v1 ArtifactVersion branch in records.schema.json | Trusted storage/metadata publication port. Human Markdown sources remain bounded; broader upload/import routes require their own exact publication contract |
| CP5 | contracts/runtime.schema.json | Native main/Supervisor/core/worker/updater mTLS peers. Renderer receives redacted status via narrow host calls; no raw IPC credential, init path or update challenge |

All JSON objects are closed unless an existing referenced contract explicitly allows an error-detail map. Body/frame bytes are capped before parsing; secrets are redacted before diagnostics. JWT shape validation is never signature validation; JSON field equality is never proof of device possession or a trusted storage write. All values are untrusted until their enforcing source, signature/session, revision and current scope are validated.

## CP1: identity exchange and24-hour continuity

Native sign-in uses a maintained OAuth2/OIDC authorization-code implementation with PKCE S256, state/nonce and DPoP key binding; Email code remains the chosen human authentication factor at the official Account service. Native main opens the system browser for authorization, owns verifier/device private key and validates the exact registered redirect/state. There is no embedded client secret, implicit grant, provider-token extraction or token in a deep link. A short-lived authorization code may use the registered callback URL per RFC8252; raw Email OTP, access/refresh tokens and session cookies never enter URLs/logs/assistant context. The Account browser transaction uses a Secure HttpOnly SameSite cookie and CSRF token; it is not an authenticated organizational session.

Protocol grounding: [RFC8252](https://www.rfc-editor.org/rfc/rfc8252), [JWT BCP RFC8725](https://www.rfc-editor.org/rfc/rfc8725), [DPoP RFC9449](https://www.rfc-editor.org/rfc/rfc9449), [fully specified JOSE algorithms RFC9864](https://www.rfc-editor.org/rfc/rfc9864). v1 allows ES256/P-256 for signed proof and DPoP, rejects none/HS*/unexpected algorithms and dynamic jku/x5u/key fetch from received tokens. Use a qualified maintained verifier, exact configured issuer/key set, explicit typ and audience, signature/time/nonce/key checks. Discovery endpoints in the OpenAPI are reserved examples, not trusted production defaults. OAuth token errors follow the standard OAuth envelope; application endpoints use the shared Euclas Error. Their exception is explicit, not accidental error-format drift.

Native callback registration is per client/platform. Desktop uses a one-shot127.0.0.1 loopback callback with unpredictable path and actual assigned port, listening only during authorization; only this callback may use HTTP under RFC8252. Mobile uses qualified claimed HTTPS app links. PKCE/state/DPoP apply in both. These mechanisms require later actual-device qualification; no broad local control endpoint is opened. All other Account traffic and local core control use verified HTTPS.

Authorization transaction persistence retains state/nonce hashes for comparison AND a service-protected encrypted parameters reference containing original state/nonce/registered redirect for the exact browser transaction. Only the auth issuer can read it; it is not ordinary log/audit/organization content. Its TTL is at most600 seconds and it is deleted when the code is consumed or transaction expires; authorization code TTL is60 seconds. The token exchange can therefore return the original ID-token nonce while preserving single-use PKCE/DPoP binding. Hashes alone are not considered recoverable state. A recovery-code confirmation is separately bound to the real current Account/session/device, fresh Email-auth transaction, exact Account revision/action digest,300-second expiry and one use. The trusted native human settings action requests/consumes it; these endpoints and credentials are never Agent/Plugin capabilities. A confirmation UUID alone does not prove consent or authentication.

The `limits` definition is the value authority:8 random decimal OTP digits,600-second challenge,5 attempts,60-second minimum resend; shared persistent limits of5 issues/address,20/client and100/network source per15 minutes. Email domain is IDNA/case-normalized by a pinned maintained address parser, local part preserved; do not strip plus aliases/dots or merge accounts. Syntax rejection is not account existence disclosure. Rate responses and issue body are uniform for existing/new/disabled identities; anonymous attempts never revoke an existing session. Code verifiers are keyed, not plaintext or brute-forceable unkeyed8-digit hashes. Expiry, attempts, issue/resend limits and consume/receipt update serialize under a shared store, not per-process counters. Incorrect verification increments attempts atomically; idempotent replay of the same failed attempt cannot reset/decrement them.

Token access lifetime300 seconds, rotating key-bound refresh family maximum7 days, no perpetual sliding renewal. Refresh reuse revokes its family; security recovery increments Account security epoch. Token endpoint follows standard single-use code semantics; a lost successful token response does not license replaying the authorization code as a new grant. Restart authorization with existing browser authentication as applicable. Secret-bearing recovery-code response replay is limited to the same currently authorized DPoP client and300-second encrypted response cache; after expiry return410, never regenerate/renew from a receipt. Ten256-bit recovery codes per set, only keyed verifier refs in ordinary persistence; replacement requires fresh human authentication and explicit confirmation. Begin recovery does not consume the code/revoke sessions; completion atomically verifies both the unused saved code and replacement Email, then consumes, rebinds the same Account and revokes sessions/challenges/old recovery set. The user signs in on the new Email and provisions a fresh set. No support/admin bypass, account merge, local owner transfer or encryption-key recovery.

The signed Instance proof is purpose/audience/local-challenge/device-bound and expires within300 seconds, with maximum30-second online skew. The Account service signs current stable subject, Account/session revisions and security epoch, verification instant and cnf.jkt; Email is absent from that proof. An ID token with the native client audience is not an Instance proof. A forwarded proof cannot enroll a different key/Instance or replay a consumed challenge. Local owner setup also requires native mTLS and the one-time OS-protected setup proof; none alone grants authority. Sign-in/revalidation does not create Membership/Grant. Account store and Instance store never share a transaction.

Local binding locks the setup/identity aggregate, verifies still-current proof/nonce/device/setup generation, inserts the one human/binding/designated owner/device/session/offline proof and receipt/audit atomically. Unique keys are listed below. A self-contained proof can be re-presented only to reconcile the same committed local admission during validity; no remote-consume-before-local-commit dependency is introduced. If the cookie/credential-store write is interrupted, query the bound receipt under the same possession proof; return metadata or rotate/revalidate the same identity under a new valid challenge, never mint another Actor/session from the UUID alone. Idempotent replay checks current authorization and never extends proof lifetime.

The sole new-baseline identity namespace is `/api/v1/setup/owner` and `/api/v1/session...` in desktop-identity.openapi.json. Account operations are in a separate service. Same-origin renderer mutations use Secure HttpOnly SameSite=Strict host-only cookies, exact Origin/Host and CSRF. Native pre-session owner/session exchange has mTLS+DPoP+one-use local nonce (and setup proof for owner), not cookie-based ambient authentication, so Unit/CSRF headers are intentionally absent there. Native revalidation also checks current cookie+CSRF. Cookie/session values never appear in JSON, preload return values or plugin interfaces.

The elapsed clock must include sleep/hibernate time: qualify a continuous native clock and its boot identity, not an uptime API that stops on suspend. If elapsed time across suspend cannot be established, wake fences protected admission until online revalidation. Restoring an old DB or sleeping for more than24 hours cannot preserve an apparently unexpired lease. These are explicit availability limits of the conservative v1 profile.

**Offline policy offline ceiling:** not_after = Account verified_at +86400 seconds, never local replay/restart time. An already verified device/session may continue existing permitted local operations only until the earlier of that bound, session expiry, local revocation or trusted-clock failure. No new login/device/invite/account change or offline renewal. Store a device/Instance/proof-bound anchor outside the movable business data directory in qualified OS-protected storage, with current boot identity, trusted monotonic milliseconds/deadline and security/revocation epochs. Same-boot reopen may reuse the exact remaining interval; restoring an older business DB must not replace the protected anchor or move the deadline. Changed boot identity, missing/tampered/regressed anchor or inability to establish trusted elapsed time requires online revalidation before protected use. v1 does not promise offline continuity across host reboot; local admin/OS compromise or cloning the protected credential store is outside this guarantee. No wall-clock rollback/skew allowance extends the24-hour ceiling.

An online proof/status check at least every300 seconds and before resuming after known reconnect checks current Account status; no new protected dispatch during pending reconnect revalidation. Network/service failure alone may enter existing offline continuity; an explicit revoked/disabled/invalid-grant/security-epoch response must immediately fence local protected admission rather than be treated as an outage. Local Actor/device/session/membership/grant revoke wins immediately in every mode. Cloud models/tools still need their own availability/entitlement; Account offline mode does not imply offline remote control or alternate paid execution.

## CP2: work/result/evidence/acceptance

Use the published proposal/commit/start/submit/verify/accept/reject/reopen commands and Work/Run lifecycle. Canonical Work satisfies `committed_work` (criteria revision, execution epoch and state-dependent committed_at), supporting content and repository scopes. The first document journey selects content scope; this task constraint is not a global Work limitation. Human intent may authorize a sequence of separate exact commands with independent receipts; proposal/commit alone never dispatch. Current criteria/source/grants/limits and dependencies are checked at start. Committing Work executing transition, one logical Run/envelope, bounded budget reservation, receipt/audit/outbox is one transaction. Model/provider calls begin only after claim commit.

Result is immutable server-registered output of a completed admitted Run, with server-allocated per-Work result_revision and canonical manifest hash of scope/work/criteria/producer/source/artifact refs. Document publication may occur while the producing Run is active; trusted completion freezes the Result after matching durable publications and producer/source bindings, before criterion Evidence is recorded. Result registration requires no criterion Evidence; Evidence subsequently binds that frozen Result. Work remains executing until explicit submit; Run success is not Work acceptance. A client submit result_revision selects that registered Result and exact set of artifact/evidence refs; it cannot register arbitrary uploaded bytes as the Run's output. Submit locks Work/admission, requires current exact revision, available bytes, no live Run and required submission evidence; it transitions to verifying per existing graph.

EvidenceInput is untrusted request data. Server binds its criterion/result to the immutable snapshot and derives verifier Actor/Assignment/kind/authority/environment from authenticated verifier context. Deterministic/independent checks require a qualified registered verifier and immutable report; a caller-provided environment UUID or method string is not attestation. Human-judgment evidence must come from the actual authenticated human and target version; model text cannot represent it. Evidence outcome not_run/fail cannot satisfy required pass conditions. Evidence binds the exact Result manifest/producer/artifacts and criteria revision; authorized source access is rechecked. Immutable report refs may contain a concise human statement; raw private reasoning and credentials are excluded.

Each Evidence has a required immutable `report_ref`. After Result freeze, for deterministic/independent evidence, a narrowly authenticated verifier records `verifier_observation` before public verify: scope/work/result/criteria/criterion, exact input artifact refs/method/outcome/environment/time/commit must match that record, whose report and verifier identity are derived by the server. Lookup by environment/target tuple is unique and checks issuer/current mandate; arbitrary uploaded reports or client Environment IDs cannot create an observation. EvidenceInput remains the existing public shape; it selects a registered observation rather than supplying trusted producer/report fields. For human_judgment, method is `human_judgment`, authenticated caller must be human with current work.verify rights, and environment_ref must match the server-registered native session/device environment shown by the current session view. The core stamps actual observed/recorded time and creates an immutable JSONB statement/report from that authenticated decision; client observed_at is informational and cannot create or backdate authority. The report uses the existing immutable JSONB artifact path, not the office-file producer branch. Do not expose verifier-observation issuance as a human/model-controlled public endpoint.

The ordered path is Result freeze → POST /work-items/{id}/evidence → submit → verify → accept. The evidence command requires current work.verify authority, exact current Result/criteria, no live Run and Work executing or verifying. It records bounded EvidenceInput using the same trusted observation/human-session rules above, creates report/Evidence/receipt/audit/outbox atomically and increments the aggregate revision without advancing Work state. Partial or failed evidence may be recorded; submit requires evidence for every required criterion, not a pass assertion. Replays return the original authorized receipt; conflicting keys, stale revisions, forged human context and changed Result fail. Evidence and verify return EvidenceCommandResponse: exact result_revision, new aggregate revision and cumulative registered evidence_ids for that Result in stable order (maximum1000; reject recording that would exceed the bound). Same-key authorized retry after response loss returns the original IDs/revision and cannot duplicate reports or Evidence. Submit/accept use these IDs; current source/result/authority is rechecked, and a newer recording requires its returned revision/set. Later commands use the returned revision. Verify is legal only in verifying; its evidence array may be empty to evaluate already recorded evidence, or add evidence under the same rules. A failed verification returns to ready with findings; missing/not_run/fail evidence cannot produce a pass.

Verify checks every required criterion under trusted evidence and moves to awaiting_acceptance only when pass conditions hold. First-slice final accept requires an actual human, separate accept authority and exact current result/criteria; authorized digital non-security review remains supported in the full product within explicitly delegated non-security review authority, not a substitute for First-slice human confirmation. A single explicit human UI action may sequence evidence recording, submit, verify and accept with distinct receipts and returned revisions; it cannot bypass either guard. Accept locks Work, rechecks current rights/evidence and atomically commits Acceptance, Work accepted revision, audit/outbox/receipt. Conflicting decisions cannot overwrite it; reopening creates a new work revision and leaves old Result/Evidence/Acceptance intact. Same-key replay returns the same permitted decision, not a second Acceptance.

## CP3: finite execution and effects

The immutable Run envelope pins Work snapshot/hash, Actor/Assignment, source/workspace/grant/capability manifests, workflow/checkpoint versions, executor/model/profile/qualification and all auxiliary routes, locale/deployment/deadline and budget reservations. First-slice route kinds are qualified local_no_api or cloud subscription_no_overage; this does not select a vendor/model/version or qualify either route. No undefined fallback or hidden summary/embedding API. Source/skill/provider output is data; only the application-controlled finite workflow may choose validated next steps. Remaining route capabilities fail closed.

Worker claim is30 seconds of DB time, renewed at most every10 seconds while active; every dispatch/complete checks current lease and work epoch plus grants/limits/deployment/readiness. A heartbeat proves liveness only. Waiting releases the live lease/model process; a persisted wait reacquires new ownership and current policy on wake. A single engine owns retries: the canonical contracts/execution.schema.json retry_policy: maximum3 total attempts including initial attempt1; attempt2 waits1 second and attempt3 waits5 seconds after the preceding failure, persisted without jitter; no fourth attempt or30-second slot, provider SDK retries disabled or included in that same total. Retrying cannot reset deadline/attempt/charge identity. G1 comparison still chooses the engine before product selection; these interfaces do not declare PG or Temporal qualified.

Action prepared intent+outbox commits before effect dispatch. Logical effect/action target digest and provider idempotency key survive retries/handover. Owner Run/epoch may change only through an auditable fenced transfer with current authority, preserving origin and unknown history. After a lost reply, status is unknown, reservation remains held and the provider operation/key is reconciled; expired provider key is not permission to resend. Callback/event source and sequence/digest are checked before state changes. Unknown/conflicting output never becomes completion. Cancellation fences first, then requests stop and records remaining uncertainty; it does not undo remote effects.

Budget reservation atomically occupies all applicable owner/Unit/provider/resource ceilings, including child/retry/auxiliary work. Dimension kinds are unique within a reservation; measured/estimated values have amounts, unknown has null (never zero). Unknown effects/usage keep the conservative reservation; settling/releasing requires reconcile evidence. A subscription-only route must prove no overage; unsupported enforceable bounds or unknown paid-call exposure refuses admission. Exact host ceilings are explicitly configured within qualified profiles, never enlarged by an assistant. Inbox/outbox delivery is at-least-once with unique source/event and digest consistency; durable commit precedes ack. Persist next continuation/checkpoint/output hashes, never credentials or ephemeral live process memory.

## CP4: generated binary documents and byte publication

First-slice publishes generated editable DOCX plus a qualified PDF/readable rendition under office-v1; human Markdown input remains an explicit separately bounded source profile. Exact MIME values, raw_binary_v1 encoding and generated producer provenance are discriminated from governed structured JSONB/uploaded Markdown. The trusted gateway derives producer Run/action/step/work/criteria/epoch from the admitted request, not the Executor's claimed JSON. Canonical Result references exact available versions/hash; a rendition names its source version/hash and pinned transform. exact fidelity requires passing declared checks, partial requires nonempty limitations, unavailable is not offered as accepted output. Cyclic rendition lineage and cross-scope sources fail.

Profile limits are exact in `document_limits`:10MiB input/output per object,50MiB total ZIP expansion,1000 ZIP entries,100:1 maximum compression ratio,100 pages,10000 paragraphs,500 tables,120 seconds and512MiB per processing action. Source/output count bounds are in their schemas. Limits are safety bounds, not promised capacity/performance; reject unsupported cases clearly. First-slice supports en/zh-Hant/de text and ordinary tables on the qualified tool/font tuple. Reject DOCX macros, executable/embedded OLE, external relationships, encrypted/unsupported packages and ZIP traversal/bombs; reject PDF scripts/actions/attachments, encrypted/unsupported inputs and scanned-only documents needing unqualified OCR. Font/tool licenses and visual CJK/table/editability checks are qualification prerequisites. Broader PPTX/OCR and original-file synchronization remain complete document qualification scope.

Prepare reserves a versioned publication intent under current Run/source rights. Trusted storage materializes durable immutable bytes, validates actual MIME/hash/size/profile and records a byte proof through its separately scoped capability. Renderer/Executor/app IDs alone cannot issue that proof. Commit locks intent, Work/admission/source authorization and storage binding in stable order, rechecks after waits, verifies exact proof/current epoch and atomically publishes available metadata/version/provenance/receipt/outbox. No SQL transaction spans processing or physical writes. Metadata never points available to missing/unverified bytes; accepted content has no mutable agent mount.

Publication lease is300 seconds; expiry does not destroy the only valid result. Blob-before-metadata crash leaves a recoverable unpublished object; retry the same intent/proof identity if still authorized or register a linked replacement intent after reconcile, never overwrite bytes. Metadata-commit response loss queries the receipt/exact version. GC can remove only owned unreferenced staging after current references/receipts/active intents/recovery holds and durable cutoff are checked. Native adapters establish root/file identity and durability on each OS; Linux dev/ino semantics are not asserted on Windows. No actual adapter is implemented by these schemas.

## CP5: native control and noninterrupting UI update

Native main↔Supervisor/core uses qualified TLS1.3 mTLS on a private loopback endpoint with pinned local application trust and per-component private keys in protected native storage. Peer registration binds component role, actual instance/controller/epoch, signed binary identity and capability; OS user/PID/port/UUID alone is not authentication. Protected bootstrap passes trust over inherited native channels, never argv/env/renderer/source workspace. Implementation must qualify the concrete OS key/peer/binary/lock mechanisms before enabling; an unqualified adapter fails startup. The first-party renderer is served with API from the same app-managed loopback HTTPS origin, exact Origin/Host/CSRF and isolated session partition, no Node integration or arbitrary preload method. Never disable global certificate verification to make local TLS succeed.

Initialization before sign-in may inspect/create a NEW qualified local data root and display needs-sign-in, but cannot dispatch. Exactly one controller holds an OS Instance lock with validated process identity; the new baseline marker has a selected manifest hash and journaled staging/publish boundary. An unrecognized nonempty target fails; never auto-adopt/reset it or mix old/new migration histories. Database readiness/identity/reconciliation/storage/worker readiness are separate. `dispatch_enabled` is true only with compatible versions, active authorized UI, current human/device/account continuity and all relevant guards; provider failure can leave permitted document/settings reads available. Secret/configuration handles are opaque native refs, not paths from the renderer.

Frame version1, maximum256KiB, UUID request/idempotency IDs, connection-issued nonce valid60 seconds/replay cache, exact request/controller/epoch and current revision checks. Responses distinguish stop_requested from stopped. Inspect is read-only; initialize/start/update require current native component role and appropriate setup/administrative authority. Stop is monotonic and reducing authority: expected_revision=0 denotes no aggregate CAS; it still validates exact controller/ownership epoch/current peer and never restarts or targets another controller. Duplicate stop returns its receipt; stale ownership fails. Stop first persists stop_generation and fences admission, then coordinates children/effects and releases ownership only after confirmed stop. Manual quit is detected by trusted native main before UI teardown and wins over any update permit. Unexpected peer/UI loss fences after at most15 seconds with5-second liveness checks; no crash/boot daemon continuation is created.

The v1 update profile is **overlap before old UI exit**. The trusted updater verifies/stages a compatible signed target and starts/registers its new native main while the old UI/controller/worker stay alive. An authorized300-second intent binds source/target manifest/protocol, maintenance operation, actor/device, replacement peer certificate, current controller/ownership epoch and stop_generation. Only that new peer can sign the one-use reattach challenge and atomically consume the intent under current session/policy. It authenticates and proves new UI readiness before the old UI exits through the authorized updater path. Expiry/failure before handoff aborts activation and leaves old UI/work running; it never cancels a long Run to meet a deadline. After handoff the consumed intent is a receipt, not a timer giving ongoing execution rights: the new app is open and ordinary lifetime rules apply.

For prepare/reattach, the core issues an ES256 `euclas-maintenance-permit+jwt` only after actual current human-session/device possession and current Instance maintenance authority are verified. The pinned local core issuer/key and Supervisor audience are required; neither renderer claims nor an actor_session_id UUID issues a permit. Its lifetime is at most60 seconds and never beyond session/identity/intent expiry. Validate purpose/jti/action digest, exact manifests, replacement peer/certificate, controller/epoch/stop_generation and current registered device at dispatch. The core rechecks live session/authority immediately before permit consumption; unavailable/revoked core authority blocks handoff while old UI remains. Consume jti once with operation receipt; same-key current-authorized retry queries the original receipt and cannot issue another handoff. Do not accept an Account identity proof as a maintenance permit. Manual stop generation always wins even over a valid signed permit.

If a platform/version cannot safely overlap, retain old runtime/UI and defer activation while active work runs. Do not use an unqualified UI-absent grace mode to enable a headless worker. Controlled-updater's broader permitted controlled relaunch can receive a separately qualified compatible mechanism later; this profile already exercises same-controller, nonduplicated relaunch without a gap. Manual quit/stop/revocation always fences even if intent/target are valid. No new Supervisor is created by reattach. Old Run handlers remain until completion/safe declared native handover; incompatible schema changes wait for old writers, required migration checkpoint and tested compatibility. A single public update channel does not mean all components activate simultaneously.

## Persistence and transaction constraint matrix

All compound foreign keys include Instance/root/Unit where applicable; public UUID equality never grants access. Private Account/credential/native journal stores have their own authority and transaction domains. Trusted command receipt/state/audit/outbox commit together in the domain that owns the command. Cross-store transitions use durable intent/verified lookup/reconciliation, not imaginary distributed SQL transactions.

| Aggregate / owner | Exact uniqueness / foreign-key obligation | Transaction / retry and failure boundary |
|---|---|---|
| Account challenge/session / Account service | Unique challenge ID; one successful consume/challenge; unique refresh family+generation; address/client/network counters shared across replicas; session Account/security epoch valid | Verify attempts/consume/grant/receipt atomically; code/auth credentials use keyed fingerprints. OAuth code lost-response restarts authorization; no raw bearer replay by UUID |
| Binding/setup/device / Instance core | Unique(instance_id,account_id), unique(instance_id,actor_id) binding; one designated owner; unique(instance_id,device_key_thumbprint); challenge purpose/device/nonce/proof_jti one use | Lock setup/account binding; Actor/owner/binding/device/session/receipt/audit commit once. Credential-store failure cannot create duplicate identity; query/revalidate same admission |
| Offline proof / core+secure store | Proof ID/source jti maps one fixed verified_at/deadline; device/Account/binding/current local epoch FK; one active protected anchor per Instance/device | Secure anchor outside rollbackable data root, fixed monotonic deadline and same boot; write interruption fails closed until verified online repair, never extends validity |
| Work snapshot/Run admission / core+engine | Immutable Work/criteria snapshots; unique(work_id,attempt); at most one live Run per Work revision; one current claim/Run with epoch | Serialize start/submit/revise/cancel with Work/admission lock. Start+Run+reservation+receipt/outbox atomic; no provider call under lock |
| Step/checkpoint/events / engine | Unique(run_id,workflow_version,step_id,attempt) completion; unique(source,event_id) plus payload digest; unique(run_id,event sequence) consistency | Persist checkpoint/outputs/next state before ack; lost notification recovers by persisted polling; conflicting content is integrity failure |

Application/worker/storage/verifier/migration roles are restricted independently in the future baseline. Workers/executors cannot INSERT trusted proof/evidence/acceptance or set arbitrary policy context; they call checked commands. Storage proof issuance and verifier observations have narrowly authenticated issuers; application publication/acceptance functions check those records/current authority under explicit transactions. Migration/maintenance keys are absent from UI and workspaces. Exact SQL migrations, maintained auth/native libraries and generated TypeScript consumers are later implementation deliverables, not files silently produced in Minimum-profile.

## Conformance and runtime obligations

The published declarative definitions specify inputs/projections and stable protocol identities. Every implementation must validate positive and negative cases, required fields, ref siblings, closed objects, variant exclusivity, limits and cross-record exact binding. The [acceptance catalog](acceptance.md) requires permitted, denied, stale, duplicate/conflicting and crash behavior for CP1–CP5. These are test specifications, not a DB/process simulator or valid cryptographic proof.

Actual maintained signature/DPoP verification, shared-store races/RLS/role isolation, OS clock/key/lock/peer provenance, real Email/provider entitlement, storage/process stop, office fidelity, crash cuts and long-task upgrade remain unexecuted. Valid JSON is not evidence that login, permission, effect, budget or acceptance occurred. Complete-release invitations/mobile/communication/plugins and broader CP1–CP5 operations require their own reviewed exact packets before code.
