## First implementation request: F02.1 native protected-key TLS qualification

**Deliverable:** a bounded native two-process qualification probe on the founder Mac candidate tuple, proving protected nonexportable component keys can perform pinned **TLS1.3 mutual authentication** through the selected native TLS adapter. This is a prerequisite experiment between separately identified native probe binaries, not a CP5 control server or a fully admitted Electron desktop_main product peer. F02.3 must separately repeat the key/peer proofs with the actual sealed Euclas Electron payload and its native adapter/role boundary; probe success alone cannot qualify that product binding. It opens no Electron window, cluster, business API or dispatcher and accepts no initialize/start/stop commands. A failed candidate produces a retained failure receipt and blocks the next increment; it does not fall back to exported PEM/PFX keys or fixture authentication.

**Prerequisites:** explicit new implementation/install/disposable-resource authority; recheck exact source facts and binary provenance/redistribution/vulnerability responsibility; select exact OS/SDK/architecture/native TLS/key tuple and source hashes before installation. Existing F01 development qualification does not qualify Electron/native TLS. Gaps CG1/CG2 below must be reviewed before their consumers. No paid signing service, certificate purchase or other spending is implicit.

**Three acceptance groups (all `not_run`):**

1. Two exact owned native processes obtain distinct protected key references without private-key bytes entering JS, argv, environment, renderer, workspace, diagnostic output or test receipts. Record public certificate/key metadata and OS access policy only; export attempts and an unregistered same-user process's key-use attempt fail. Prove actual TLS1.3 mTLS with exact local trust, role/certificate pins and no public CA fallback, global verification bypass or TLS1.2 downgrade. A successful signature alone is insufficient.
2. Bootstrap trust reaches only the intended child over an explicitly inherited native channel with restricted inheritance; sibling/unrelated child, substituted binary/root, wrong role/certificate/Instance/controller/epoch and reused bootstrap material fail. Registration is based on verified native executable identity and protected local policy, never a caller-provided UUID/path/PID. Parent channel loss before registration leaves no admitted peer; positive possession and current registration are both required.
3. Repeat on real native processes with wrong trust root, expired/revoked peer, replayed challenge, malformed/oversized/truncated TLS input (no CP5 application framing exposed by this probe), failed handshake/launch and crash before/after protected-key creation/registration. Bound time/resources, close exact handles/listeners and prove no owned survivors. Preserve unknown key/registration effects by original operation ID; never delete another key/root/process. Independent exact-source review must PASS before F02.2 consumes the adapter.

**Likely ownership:** future `native/macos/` probe, its focused native acceptance test, and its short tuple/evidence record (at most three owned areas; paths are proposals, not existing commands). Pin a minimal native executable/API adapter, not a new network service/dependency framework. Verification entry point is **to be implemented**, with stable name/arguments/resources recorded before use; no `just`/package command is claimed available. A manually supplied certificate or a standard Node TLS fixture cannot pass this increment. Windows must independently satisfy the same proof in F02.5; failure on either platform prevents claiming that platform supported.

## Process, trust and ownership design

The packaged direction is Electron main + sandboxed renderer, an independently launched native Supervisor hosting/owning core policy and restricted DB integration, and separately owned PostgreSQL/worker children as needed. Supervisor is never Electron main, a renderer, `utilityProcess`, or an unqualified Electron run-as-node process. Its chosen executable/runtime/packaging needs exact qualification. On macOS, validate Euclas payload/manifest identity as well as executable signing: a signed stock Electron running changed JS is an untrusted-peer negative. Candidate Electron ASAR integrity validation plus only-load-from-ASAR fuses must be set before signing and tested; neither is proof of protected credential entitlement or release readiness. Electron embedded Node and the accepted host Node are different tuples; native ABI compatibility is tested, not assumed.

Main handles native quit detection, narrow native UI mediation and renderer delivery; Supervisor owns Instance gate/epoch, native command admission, durable lifecycle journal, core/DB readiness and child stop. For the minimal process layout the Supervisor hosts core policy and uses the canonical `core` component role; `supervisor` is not a wire role. `desktop_main`, `worker` and `trusted_updater` remain the other canonical roles. The core role does not acquire human/session maintenance authority before F03/F04, and desktop_main cannot issue core-signed permits. Any later split needs reviewed current role/key/capability registration, not a new handwritten role enum. A separate native TLS bridge is permitted only if its local signing/transport seam is authenticated, non-exporting, bounded and reviewed; it cannot introduce an unauthenticated localhost bypass behind mTLS.

Renderer has `nodeIntegration=false`, `contextIsolation=true`, sandbox enabled, restrictive CSP, no remote content or raw ipcRenderer, filesystem, shell, DB socket, native key or privileged maintenance export. Preload exposes only generated bounded view/control operations with validated sender/frame URL and current authority; it never accepts arbitrary channel names, command strings, paths or certificate decisions. TLS trust exceptions, if required for app-local HTTPS, must match only the pinned local server/certificate/origin in the dedicated session and reject all others; no global `ignore-certificate-errors` or disabled verification. Main must not become a generic signing oracle. Development rendering is not a signed distribution claim.

Duplicate app launch uses Electron's single-instance affordance for UX only. The native Instance gate remains authoritative even if Electron locks fail, different app versions overlap or multiple data roots are selected. Ordinary duplicate UI focuses/attaches only under a current registered role; it does not add a dispatcher. The CP5 maximum two live UI IDs exists for controlled update overlap, not a headless grace mode.

## Command admission and durability matrix

Only `request.oneOf`'s six existing command names are planned; no shell/renderer API or implicit maintenance opcode. `request`, `response`, `runtime_status`, `peer_binding`, `limits`, `version_set`, `initialization_journal`, `relaunch_intent`, `reattach_challenge/claims/header` and `maintenance_permit_claims/header` retain their canonical meanings. Generated closed validators run before trust/state use and on all outputs/files/queue/DB results. No unknown keys, `any`, unchecked casts or schema substitutions.

Proposed CG3 transport is four-byte unsigned network-order byte length followed by one UTF-8 JSON object; length is 1–262144 body bytes, bounded before allocation. No compression/batch/implicit resynchronization; invalid length/UTF-8/JSON/variant closes the connection with bounded redacted diagnostics. This framing must first be committed to the existing CP5 normative owner under future scope. Per connection issue cryptographic nonces, valid at most60 continuous elapsed seconds with one-use replay cache; cap connection/input/output/queue/time as below. Transport authentication never replaces current role/policy.

Before every admission/replay/query, verify current protected peer/role, Instance/controller/ownership epoch, root and compatible versions; recheck after any lock wait. Persist canonical validated command digest, original operation/effect/idempotency/receipt identity and intent **before native effects**. Do not reuse a nonce to recover a lost reply: use a fresh issued nonce and query/retry original operation. CG3 must explicitly settle exclusion of transport nonce/request_id from semantic operation digest for product CP5; same key + changed semantic content conflicts. Preserve F01b's internal stricter request hash: adapter reuses the original F01b request unchanged behind the native operation, never rewrites its transport fields. Replaying an authenticated operation may return its immutable receipt only under current authority; return current status separately, never use an old success to re-enable dispatch.

## Runtime and stop state ownership

Use only `deployment-lifecycle.runtime.edges`. First setup boot: stopped→starting→recovering; remain recovering with needs-sign-in reasons or enter needs_attention on a blocking fault. Do not label ready while identity/other required readiness is absent. Independent projections reflect actual observations: DB/core may be true while identity/storage/reconciliation/worker false. Before F03/F04 and Q lanes, `identity_ready=false`, `worker_ready=false`, `dispatch_enabled=false`; no synthetic owner/Actor/provider satisfies a guard. A visible window does not imply ready. A permitted missing provider may retain authorized reads without enabling worker dispatch.

Stop from starting/recovering/ready/maintenance/needs_attention uses stopping; stopping→stopped only after verified owned descendants, core and DB are stopped and native effect status is reconciled. stopping→needs_attention is permitted when stop cannot be proven; the admission fence stays set and ownership/gate remains held by a verified guard until all relevant holders exit. A process crash cannot persist a fiction of its own ongoing lock: inherited/retained native handles or a separately qualified app guard must keep exclusion, and reopen refuses new writers if that proof is missing. Native probes must demonstrate the actual orphan behavior. No lock-file deletion or absence of a heartbeat proves stop.

Manual closing the app, including final-window close, invokes the same fence/stop path as explicit quit; minimizing an open app does not. Trusted main captures native window-close / before-quit intent before renderer teardown; do not keep the normal macOS Electron app-active-with-no-window pattern as runtime authority. Windows session-end/forced termination may skip JS quit hooks, so native independent loss handling is mandatory. Stop detection remains independent of a renderer request. If persistence fails, immediately deny new admission in memory/native gate, surface needs_attention and retain ownership/unknown effects; do not acknowledge durable stop or drop the gate. A trusted native watchdog must also deny execution on authority loss even if SQL is unavailable.

Main/UI and Supervisor/core exchange liveness every5s; missed/invalid authenticated liveness fences by15s at the latest. Each side needs independently enforceable loss handling: Supervisor fences on main/UI loss; main/native ownership guard fences/stops exact children on Supervisor loss. A hung controller cannot be trusted to cooperate; native handle/containment authority must demonstrate no descendant can admit new effects. Killing a test dummy is not proof of harness containment; later Q2/F08 repeat this with actual workloads. In F02 there is no dispatcher to simulate as accepted real work.

Use sleep-inclusive continuous elapsed clock plus qualified boot identity, not wall time or a timer that stops during suspend. No boot-identity provider is currently selected/qualified: invalidate runtime authority and all pending transport challenges on every Supervisor restart; protected offline Account anchor continuation remains separately gated on F03/F04 clock/boot qualification. A fresh process counter is never proof of persisted same-boot continuity. On sleep/hibernate revoke relevant readiness/fence before any effect, on resume evaluate elapsed/auth/ownership before reopening admission. Missed5s/15s windows cannot be extended by clock rollback or callback delay; on uncertain clock/boot identity fail closed. Suspend notifications are hints, not proof. Reboot/logoff never auto-starts work or a daemon. Reopen is deliberate and reconciles all unknown native/DB operations and later effects before current-authorized readiness; missed schedules later coalesce once under their own guards.

Child restart proposal to settle under CG5: at most three transient restarts per rolling300 continuous seconds, delay1/5/15s for attempts1/2/3, counts/deadlines durable; no fourth. Only Supervisor restarts its verified children while app is proven open/awake/current and stop_generation unchanged. Authentication/version/schema/corruption/root faults immediately needs_attention; no automatic Supervisor resurrection. This is distinct from CP3's total-three-attempt1/5 effect retry policy and must not nest hidden retries. Final values need native test evidence, not a performance promise.

## Required native fault and concurrency acceptance

Each row is a real OS process/DB/file cut under future explicit authority, not a JSON fixture or passing planned command. Record exact cut, process handle, boot/clock, persistent records, original IDs/keys/receipts, measured fence interval and verified cleanup. Actual destructive tests touch only registered disposable resources. Never leak the Instance lock FD/handle to a renderer, worker or unrelated child. macOS duplicated flock descriptors share one lock and an explicit unlock can release it for all holders; Windows LockFileEx inheritance is not equivalent. Any retained trusted guard/DB gate arrangement must demonstrate both exclusion after controller death and no child-controlled unlock. If no safe owner survives, admission stays blocked until verified owned stop; no boot daemon or ambient rescue authority is added.
