## Filesystem ownership and recovery

The harness registers a freshly exclusively created private root, parent and socket directory. Check every path component with lstat/realpath: no symlink, unsafe permissions, wrong OS owner or changed device/inode. Bind root identity to resolved path, device/inode and data_location_id with SHA-256. A source-controlled tiny C launcher uses `open(O_NOFOLLOW)` + fstat regular-file/owner/mode/link checks and nonblocking `flock(LOCK_EX)` on the registered sibling lock, then execs the initializer while retaining the FD. The OS releases this gate on SIGKILL; no PID-only stale-lock deletion. A competing command fails busy before writes. Recheck identities at each effect/publication; unsupported hostile same-UID path replacement is not claimed prevented by portable Node path checks (F02 native descriptor-relative qualification remains required).

Initially require an empty registered root. Its only recognized entries later are the exact validated journal, staging tree and installation marker, plus explicitly journaled atomic-write temporary bytes. Unknown/nonempty targets, malformed/oversized journal, symlink/hardlink, mismatched request/root/staging/cluster identity, missing previously recorded paths or replaced inode fail closed and are retained. Staging identity is durably recorded before initdb. Journal updates and marker publication use exclusive no-follow temporary files, file fsync, atomic rename and parent fsync; unrecognized partial temp files block instead of being removed. Only the journal's next safe phase may run; never change operation IDs to escape an unknown effect.

| Boundary | Durable enforcing owner | Recovery |
|---|---|---|
| Before planned journal | Filesystem + exclusive gate | No native effect; empty root may execute original request |
| Planned → staging | Fsynced journal, then private staging mkdir/identity | Missing known staging may be created only before identity recorded; unrecorded existing staging blocks |
| Staging → initdb | Fsynced intent and exact staging identity | Before native effect resume; partial initdb remains blocked/retained; completed compatible cluster may be reconciled through pg_controldata, exact version/bootstrap catalog and recorded staging, without rerunning initdb |
| Database initialized → SQL | Validated cluster system identifier + journal | Start only that owned cluster; no credentials/default server discovery; SQL transaction applies baseline and receipt once |
| SQL commit → schema_applied | PostgreSQL durable receipt, exact original request/hash | Response loss queries original SQL receipt; never apply conflicting baseline or regenerate effect keys |
| Schema applied → publication | Verify SQL roles/current authority/identity and cluster bytes first; fsynced marker | Before marker resume verification; existing exact marker reconciles original receipt; differing bytes block |
| Published → verified | Fsynced marker, parent and final journal | Same receipt after crash; no product dispatch or implicit activation |

Keep a durable receipt intent before SQL; SQL receipt and local marker share one original receipt ID/revision. SQL state can be ahead of local journal after crash, never behind published success. Reconcile by verified lookup, not an imagined cross-store transaction. Do not run native process/network calls inside a DB transaction. No delete/reinitialize recovery path exists. A partial/unknown state returns needs-attention with retained data, not false success.
